## Failure and restart evidence

The campaign exercised two different recovery situations. They should be interpreted separately.

### MPAS00 bootstrap failure

The first MPAS00 PBS submission (`471015.pbs-ha`) failed before the model started because the historical source case contributed an obsolete setup-script path:

```text
/p/projetos/monan_das/joao.gerd/projects/mpas-bmatrix-global/scripts/load_jaci_env.sh
```

The job terminated before producing MPAS logs or scientific outputs. The workflow stopped at `mpas00_validate` and did not release downstream stages.

The replay materializer was corrected so newly materialized corrected replays do not inherit historical `mpas.pbs.setup` scripts. For this already-running case, the five MPAS00 tasks (`prepare`, `submit`, `wait`, `validate`, validation check) were explicitly reset. The valid JEDI00 work was preserved and only the MPAS00 block was rerun.

This demonstrates selective recovery when the affected task block is explicitly invalidated.

### JEDI06 state-schema guard

The next interruption occurred at `jedi06_prepare`, before any PBS submission, when the older scalar state-count contract expected 62 variables but the replay MPAS06 state correctly contained 63 variables including `refl10cm`.

After the first-cycle/cycling distinction was encoded, the failed `jedi06_prepare` task executed again. All previously successful upstream work remained available and the workflow continued through JEDI18.

This demonstrates normal restart from a task that is already in a failed state.

### Remaining restart-safety requirement

The first replay did **not** test the case in which a task that had already finished successfully is changed and rerun while its dependent tasks also have old successful state recorded.

The final engineering review found that `simpleWorkflow` must propagate that rerun to dependent tasks; otherwise a new `prepare` result could be combined with an old `submit`, `wait` or `validate` result. This is tracked in `joaogerd/simpleWorkflow#11` and PR #13.

Until that correction is incorporated into the `simpleWorkflow` version used by the campaign, the validated evidence is limited to:

- restart from a failed task;
- preservation of unaffected upstream work;
- selective recovery after explicitly resetting an affected task block.

It should not be described as automatic invalidation of every downstream successful task after an upstream change.
